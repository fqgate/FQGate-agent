# Agent 与 MCP Apps 自动发布

公开仓库有两条独立发布线：Agent 插件安装包使用 `v<版本>` GitHub Release；MCP Apps 使用经过 Ed25519 签名的 `fqgate/mcp-apps` 稳定目录。它们与 FQGate 主程序分别管理版本，不能把版本号混用。

## 一次性设置

1. 在 Settings → Actions → General 中把 Workflow permissions 设为 `Read and write permissions`，并允许 GitHub Actions 创建 Pull Request。
2. 创建 Environment `agent-production`，设置 required reviewer。它控制 Agent Draft Release 何时正式公开，不需要额外 Token。
3. 创建 Environment `mcp-apps-production`，不要设置 required reviewer，并添加 secret `FQGATE_MCP_APPS_ED25519_PRIVATE_KEY`。该环境只用于隔离正式签名私钥；正式发布标签或手动触发工作流本身就是发布授权。值必须是与 `fqgate/mcp-apps/mcp-apps-ed25519-public.pem` 匹配的 Ed25519 私钥 PEM；不得把私钥写入仓库、日志或构建产物。
4. 创建 Environment `gitee-production`，不设置人工审批，添加 secret `GITEE_TOKEN`。令牌属于 Gitee 用户 `qicuo`，只授予仓库操作所需的 `projects` 权限，用于推送 `qicuo/tonghuasun-agent` 主分支、标签和发行资产。
5. `main` 必须允许发布工作流在 Release 公开后提交 `update/stable.json`、版本清单和 `.claude-plugin/marketplace.json`。如果分支规则禁止 Actions 直接更新主分支，先按仓库治理要求配置发布自动化写权限，否则稳定通道不会切换。

FQGate 镜像同步复用 `gitee-production`，不设置 required reviewer。同步工作流每 15 分钟读取 FQGate 官方稳定清单；发现 Gitee 缺少对应标签、发行资产或主分支提交时自动完成同步，已同步版本会跳过重复上传。

GitHub 仓库内部的发布全部使用自己的 `GITHUB_TOKEN`，不需要自建 GitHub App，也不需要 GitHub 跨仓库 PAT。只有向 Gitee 写入镜像时使用独立的 Gitee 私人令牌。

## 发布 Agent 插件

1. 在 Actions 页面运行“准备 Agent 插件发布”，选择 `patch`、`minor`、`major` 或 `custom`，并填写每行一条的更新说明。系统从当前 Agent 版本自动计算新版本；只有选择 `custom` 时才填写完整版本号。
2. 工作流会同步八个适配器、SDK、安装器和文档版本，构建九个确定性插件包，生成 SHA-256 和候选发行清单，然后创建 `release/agent-v<版本>` PR。
3. 检查并合并 PR。主分支会重新构建同一批安装包，并要求每个字节与候选清单一致。
4. 工作流先创建 Draft Release。批准 `agent-production` 后才公开 Release；拿到 GitHub 的真实发布时间后，最后切换稳定清单和 Claude 市场入口。

审批期间 Claude 市场仍指向上一个稳定版，不会提前跳到尚未公开的下载包。已公开 Release 不会被恢复任务覆盖；同版本重跑时会下载远端资产并校验一致性。

## 发布 MCP Apps

1. 正式发布推荐创建并推送 `mcp-apps-release-<版本>` 标签；也可以在 Actions 页面手动触发，选择 `patch`、`minor`、`major` 或 `custom`，并填写最低支持的 FQGate 版本。系统从当前 MCP Apps 版本自动计算新版本；只有选择 `custom` 时才填写完整版本号。
2. 工作流会自动安装锁定依赖、运行测试、构建 UI、使用正式私钥签名，并立即用仓库中的 FQGate 公钥验签。标签名必须与计算出的版本一致。
3. 验证通过后，工作流自动提交并推送 `main`，再检查 GitHub 原始文件稳定入口是否已经指向新版本；不再创建等待人工审批的发布步骤。
4. `main` 的 MCP Apps CI 成功后，“同步发布到 Gitee”会自动验签，并以仅快进方式把同一提交推送到 Gitee。Gitee 出现独有提交时同步会失败，不会强制覆盖。

## 故障恢复

- Agent Draft Release 阶段失败：修复问题后手工运行“发布 Agent 插件”，填写与 `fqgate/compatibility.json` 一致的版本。
- Agent Release 已公开但稳定清单提交失败：先修复主分支写权限，再用同一版本重跑。脚本只接受内容一致的已公开资产。
- MCP Apps 签名失败：检查 `mcp-apps-production` 的 Environment secret 是否为匹配公钥的 PEM，不能改用临时密钥发布。
- MCP Apps 稳定入口校验失败：先确认发布提交已经进入 `main`，再检查 GitHub 原始文件缓存或重新运行同一个发布标签；不要直接改写已签名资源。
- Gitee 同步失败：修复 `gitee-production` 的令牌或处理 Gitee 独有提交后，手工运行对应同步工作流。FQGate 同步工作流可填写版本恢复；同名资产必须与 GitHub 完全一致，否则流程拒绝覆盖。

Gitee 同步只处理已经公开且校验通过的 GitHub Release。MCP Apps 发布从标签到 GitHub 稳定入口、再到 Gitee 同步均自动完成；FQGate 发布后由定时同步工作流自动完成镜像；Agent 发布仍保留 `agent-production` 的人工审批。Agent 和 FQGate 同步都会下载公开 Release 资产，按 SHA-256 校验后创建或补全 Gitee Release。任何远端同名文件不一致都会使流程失败，不会静默覆盖。

版本号只表达组件自身的演进，不用来推断 FQGate、Agent 与 MCP Apps 之间是否兼容。`major` 是显式产品决策；从 `0.x` 升到 `1.0.0` 可以只是宣布稳定。Agent 只通过 `fqgate/compatibility.json` 的 `fqgate.minimumVersion` 声明最低 FQGate 版本，不设置版本上限；MCP Apps 使用 `minimumFqgateVersion` 独立声明最低版本。安装、配置和启动检查均按最低版本执行。

兼容清单和启动脚本会随插件安装包一起分发。已安装的旧插件需要更新后才能采用新规则；只修改仓库中的清单，不会改变用户电脑上的旧副本。
